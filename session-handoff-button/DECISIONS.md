# Decisions: session-handoff-button

## Decisions
- The button is drawn in the `AbovePrompt` band. Rejected: the status line, because the `statusLine` setting is a command's output and no render site exists for it; `$.ui.status`, because it takes plain text and cannot be pressed; `PromptHint`, because its `tail` is text only and replacing its tree removes the engine's hints.
- The handoff is written by a real turn of the person's skill (`$.command.run`). Rejected: `$.model.fork`, because a fork denies every tool, and the skill runs read-only checks (git status) to reconcile state.
- When the configured skill is missing, the mod sends a built-in handoff prompt, so the shared mod works for people without the skill. Rejected: refusing to run, because the shared repo would do nothing for most people.
- The handoff turn is identified by the first main-loop `turn.start` after the press, and its `turnId` is kept in `$.state`. Rejected: matching the turn text, because what a skill command's turn carries as `text` is not documented.
- `/clear` and the submit run from `$.clock.after`, not from inside the `turn.complete` hook, because `$.command.run` rejects inside a hook the turn waits on.
- `/clear` runs only after the handoff turn ended with reason `answer`, not aborted, with non-empty text. Rejected: always clearing, because a failed handoff would lose the session with nothing to continue from.
- The fresh session gets a short message (`Session Hand-off: continuing from the previous session (handoff saved at <path>).`), sent with `asUser: true`, and the handoff itself goes in first as a user-role row from `$.session.append` that the person does not see as typed. Rejected: pasting the whole handoff as the message, because it fills the screen and the person asked not to see a paste; `context` on a `prompt.submit` hook, because a plugin's own `$.prompt.submit` skips that plugin's hooks (seen in the test kit: the hook never ran for the mod's own submit) and `context` only rides one prompt; a `prompt.compose` system section, because it is not in the transcript, so the model would lose it after the first request. `autoSend: false` is the opt-out for anyone who wants to read the short message first.
- If `$.session.append` is refused or throws, the full handoff text becomes the message, so a refusal never loses the handoff.
- The handoff is saved to `<TMPDIR or TEMP or /tmp>/session-handoff/handoff-<timestamp>.md` before `/clear`, and its path is in the short message. It replaces the old clipboard copy: it survives a failed `/clear`, does not overwrite what the person copied, and the path tells them where to find it. Rejected: `$.store`, because it outlives the session and is capped at 4 MiB in all; the project folder, because it would dirty the working tree. One file per press, never deleted by the mod (the API has no delete), because a shared fixed name would let two sessions overwrite each other. If the write fails, the handoff is still delivered, without a path.
- The 65% guard is a `prompt.submit` hook that answers `{ drop: reason }` once, for the person's own prompts (composer, bridge) only. Rejected: stopping the running turn (`$.turn.abort`), because the request was to stop the next message and a half-finished turn is worse than a warning; stopping every time, because it would nag. It never stops slash commands (so `/compact` and `/clear` always work), plugin prompts (so the handoff itself runs) or anything while a handoff is running. It warns once per crossing: the flag resets when the context falls under 65% or on `session.start`.
- After a drop the mod puts the draft back in the box if it is empty (150 ms timer, `$.prompt.read` then `$.prompt.fill` in replace mode), so the warning costs a second Enter and no retyping. Whether the engine already restores it is not known; the check makes either case safe.
- The guard is advisory: no `.catch` on the hook, so a broken guard lets the prompt through (the documented default for `prompt.submit`), because a bug in a warning must never block the person's work. `claude plugin validate` lists it as a gating hook without `.catch` on purpose.
- Colors are fixed bands at the person's thresholds (under 45, 45–64, 65 and up), not interpolated, because the thresholds were stated as ranges. Hex values, not theme keys, because the request named green, orange and red and the theme's `warning` may be yellow.
- A green context draws the chip and `Context clean` as plain `Text` instead of the Button, so there is nothing to click and the `h` hotkey is gone. Rejected: a disabled Button, because `ButtonProps` has no disabled prop in 2.1.295; keeping the Button and ignoring the press, because it would still look pressable. While a handoff is running the Button stays, whatever the color, so its progress label stays visible. An unknown percent (`–`) keeps the Button.
- `phase` is reset to idle on `session.start`, so a reload mid-handoff cannot leave the button stuck in "Writing handoff…".

## Assumptions not verified (updated for 1.0.0)
- `$.command.run({ command: 'clear' })` runs the built-in `/clear` from a plugin. The types say it runs a command "as if the person typed" it and that the command list includes built-ins. Seen live on 2.1.299: the transcript cleared. If it fails, the press ends with the toast "/clear failed; the handoff is saved at <path>".
- `$.command.run` of a skill command raises `turn.start` and `turn.complete` like a typed prompt, and `answer` holds the full handoff. If wrong: the mod waits in "Writing handoff…" until the next turn, or sends only part of the handoff. How to check: press it once and compare the saved .md with the skill's reply. The live run on 2.1.299 used the built-in prompt route (the isolated test config has no handoff skill), so the skill route was not exercised in that run.
- `$.prompt.submit` sent right after `/clear` resolves lands in the fresh session, not the old one. Seen live on 2.1.299: the short message was the first message after the clear.
- A single click on the band's Button presses it, not just focuses the band. The Button docs say a click raises `ui.press`; the band docs say a click focuses it. If wrong: it takes two clicks, or a click then `h`. How to check: click once in a real terminal.
- Reload survival: designed for (`$.state` keeps all three keys), unverified; no stage proves a reload.
- `$.session.append` right after `/clear` lands in the fresh session and is read by the model without being drawn. Seen live on 2.1.299 in the terminal: the model answered a question only the old session knew, and the handoff text was not on screen. Not checked on the Desktop Code tab, where a user-role row may be drawn differently.
- The live runs used a scratch copy with lowered thresholds (button from 1%, guard at 1% or 90%), so the real 45% and 65% marks are covered by the unit tests only.
- The saved file takes the default permissions. On macOS TMPDIR is private to the user; on Linux `/tmp` is shared, so the handoff may be readable by other local users. The mod cannot set permissions.
- Not checked on the Desktop Code tab.
